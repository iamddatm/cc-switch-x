# CC Switch X v0.18.0

这一版补上 Skill 侧的落盘核对：启用矩阵说「已启用」的东西，盘上那份还是不是我们管的。此前这一类不一致只有在你点开关的那一刻才会暴露。

## 为什么需要它

与 cc-switch 这类工具并存时，两边都往同一个 `<agent>/skills/` 目录写。Skill 既不进 `state/applied` 台账，也不在 `services::drift` 的字节比对范围内 —— 于是会出现这种状态：面板与 `agents/<id>.json` 矩阵都显示已启用，实际生效的却是对侧那份旧内容，而且没有任何地方告诉你这件事。

## Skill 勾选与落点核对（只报告）

- 新增 `services::skill_verify`：从**启用矩阵**出发（与 v0.17.0 的「未纳管」扫描恰好相反方向），对每个 `switchable(Skill)` 的 agent 逐条核对落点归属，复用既有的 `adapters::skills::ownership` 判定口径，不另立一套。
- 三类结果，各自都说清下一步：
  - **被别处接走**：落点在，但已经不是我们的 —— 是别人的链接时 `detail` 会把**链接当前实际指向**原样写出来（例如 `~/.cc-switch/skills/brainstorming`），一眼看出是谁接走的；是我们没部署过的目录时直说。
  - **落点不见了**：被外部删掉，或从未部署成功。
  - **勾选悬空**：真源已经不在了，只剩矩阵里那条勾选；矩阵里出现拼不出真源路径的 ID 也归这一类。
- **只报告，绝不动盘**：核对不建链接、不补目录、不改真源，也不写 `index.db`（现算的派生数据，与未纳管扫描同一口径）。
- **没装的工具不报缺失**：配置根不存在的 agent（矩阵里只是历史残留）整条跳过，避免制造几十个假问题淹没真问题；判定沿用检测门禁的 `NotDetected`，其他读取失败照常报错，不静默降级。
- 新增 IPC `verify_skill_deployments`：纯只读的本地目录遍历，走 `spawn_blocking`，不占 Skill 写任务互斥锁（与 `scan_unmanaged_skills` 同一口径）。

## 接入位置，以及「点完开关横幅不更新」

- 顶部状态条新增一条计数：`N 个 Skill 已勾选但落点不归本工具管，请到 Skills 面板核对`；与原有的漂移条分列，两类问题都只在真有问题时出现。
- Skills 面板顶部新增 `SkillDeploymentNotice`：逐条列出 `agent / skill：实际情况`，带「重新检查」。问题为 0 时整块不渲染。
- `useDrift` 升级为一次核对两类问题 —— 台账类资产的字节漂移 + Skill 的勾选归属，共用同一个重扫入口与广播事件，所以设置面板原有的「重扫落盘」现在也会刷新 Skill 核对，两处数字不会各说一套。
- Skills 面板任何一次勾选/取消/批量操作之后都会重读一次落点核对。真机跑第一轮时发现：不重读的话横幅会停在改动前的计数上，继续点名刚刚已经处理好的那条。

## 顺带修的既有缺陷：外来落点「既启不了也关不掉」

落点被别的工具占据时，取消勾选原本也会失败 —— `skills::remove` 返回 `Removed::Foreign`，`set_enabled` 的取消分支把它当成失败，矩阵记录清不掉，于是这条勾选既启不了也关不掉，只能手改 `agents/<id>.json`。现在：

- **取消勾选只退账不动盘**：清掉我们矩阵里的记录，别人目录/别人的链接一个字节都不碰，实测标签返回 `detached`（`commands/agents.rs` 的单条命令与 `skill_source::set_enabled` 的批量命令同一口径）。这与 `uninstall_one` 早已有的处理一致 —— 卸载遇到外来落点本来就是「保留 + 清矩阵」，启停这条路不该比卸载更硬。
- **重新勾选照旧被能力闸拒绝**：`不是本工具部署的，未做改动`。要恢复部署仍然得先清掉对侧那份同名条目。
- 横幅文案因此给出两条出路：对侧取消同名后再重新勾选；或者干脆取消勾选退账。
- 核对报告里的真源路径统一成 `display_path` 形态。`storeRoot` 是从 `settings.json` 读进来的正斜杠路径，与 Windows 反斜杠拼接后 `Path::display()` 会输出 `C:/…/store\assets\skills\x` 这种混用分隔符，跟同一份报告里另一条也不是一套写法。

## 未做（留待后续）

- **反向核对**：盘上还挂着我们部署的链接、矩阵却已经取消勾选（例如删真源后残留的坏链）本次不报。坏链仍按「我们的」处理。
- **Rules / Subagents 的同类死路**：这两个整文件资产在取消勾选遇到外来文件时仍然返回「不是我们落的文件，拒绝删除」，同样清不掉勾选。它们的处置纪律是「先裁决漂移再动盘」，是否也补一条「只退账」需要单独定夺，本版没有顺手改。
- junction 被外部 `remove_dir_all` 递归删穿进真源这条风险路径仍未实测（对侧工具是否真的判不出 junction，取决于它的 `is_symlink` 实现）。

## 验证

- `cargo test`：**613 lib + 3(`asset_chain_e2e`) + 2(`sessions_e2e`) 通过**，无告警（v0.17.0 是 606 lib）。新增 7 条用例：勾选与落点一致时保持安静、链接被别处盖掉时报出实际指向且真源未被触碰、我们从没部署过的目录算外来、落点被删时报缺失且**不顺手补回链接**、真源被删时报勾选悬空、未安装的 agent 整条跳过，以及取消勾选外来落点时「退账 + 不动对方文件 + 矩阵真的清掉」。测试全部用临时 store + `baseOverride` 沙箱，不碰本机真实 `~/.claude`。
- `pnpm test`：**231 通过**（27 个文件，v0.17.0 是 228）；`SkillDeploymentNotice` 3 条（空清单不渲染、逐条点名并给出两条处置方向、「重新检查」交给面板重扫），另在 Skills 面板用例里钉住「开关之后要重读核对」。`pnpm build`（含 `tsc -b`）、`cargo check` 与 `node scripts/check-release-version.mjs` 通过。
- **真机验证**（Windows，临时 store + `baseOverride` 沙箱，`seed-ui-e2e.ps1` 铺数据后用 CDP 驱动，跑完已 `-Restore` 还原本机 `settings.json` 并清掉沙箱）：
  - 三种形态都如实报出 —— `hijacked=foreign`（`detail` 写明落点现在指向 `…/sandbox/rival/skills/hijacked`）、`vanished=missing`、`dangling=sourceGone`；指向我方真源的 junction 部署 `managed-skill` **没有**被误报成外来。
  - 状态条显示「3 个 Skill 已勾选但落点不归本工具管」；Skills 面板横幅逐条点名并给出恢复方向。
  - 核对确实不动盘：对侧 junction、对侧正文、我方真源正文在核对前后逐字一致，也没有顺手补链接。
  - 退账改动之后复跑：批量取消勾选返回 `ok=[{hijacked, "detached"}]`、`agents/claude.json` 里那条已经清掉、对侧 junction 与正文原样、再核对只剩 2 条；单条命令 `set_skill_enabled` 同样返回 `detached`。重新勾选那一次照旧被拒（矩阵不再含该条，说明失败后没有误写矩阵）。
- **真机未覆盖**：横幅/状态条在「用户真的点复选框」之后的即时刷新只有单测证据（真机是通过 IPC 直接改的，绕过了 React 订阅链，因此当时状态条仍显示旧计数，这正是我们补上重读的原因）；`dangling` 这类非法 ID 勾选只在单测里构造过。
