# CC Switch X v0.20.0

v0.19.0 发完，真机上三处体验同时卡手：Skills 页 83 个 Skill 要逐个点勾选；Agents 页只说「CLI 已安装」，看不出这台机器上装的是哪一版、上游出了什么新版；还有几处列表鼠标划过没有任何反应，找不到自己在哪一行。这一版把这三件事一起收掉。

## 列头批量开关：只 Skills 页，且不是「一键翻转」

- `AgentColumnsHeader` 里那句「批量开关留到下一轮」兑现了。列头从静态格子变成可点的入口，点开是**两个动作**——「启用剩余 N 个」与「全部关闭」，外加一行「已启用 N / 共 M 个」和一行作用范围脚注。
- **刻意不做单击翻转**：一次误点就把几十个落点全关掉，代价和「省几次点击」完全不对等。对齐上游 cc-switch 的 `MatrixColumnHeader` 口径（MIT 声明已补进 `THIRD_PARTY_NOTICES.md`）。
- **作用范围是当前筛选结果，不是整个库**：脚注会把这件事写在菜单里（`仅当前筛选结果 · N 个` / `全部 Skill · N 个`）。搜索、来源、仓库、Agent、状态五根轴里任何一根收窄过，批量就只动看得见的那些。
- 能力闸在列头这一侧也生效：只有 `switchable`（既支持又实测）且配置目录已就绪的列才给入口，Gemini 的 Skills 这类未实测落点仍是静态格子。顺带记一笔：`agentsForType` 只过 `supported`，所以已有的批量条会把未实测 Agent 也列出来、靠后端 `Unsupported` 报错兜底——这个既有毛病没在新列头里继承，但也没去改批量条，属另一笔账。
- 复用而不另立：`SkillsPanel` 的 `setEnabledFor(agentId, enabled)` 泛化成 `applyBatch(agentId, ids, enabled)`，批量条与列头走同一条路径、同一套播报（`启用完成：成功 N 个，失败 M 个` + 逐条原因），后端仍只有一次 `set_skills_enabled` 调用。批量结果**必须走 `refreshAll`**（含 `deployment.rescan()`），否则落点核对横幅会停在改动前的计数上。
- MCP 页共用同一个列头组件，但没接线 `bulk`，保持原样静态——本版按需求只做 Skills。

## Agents 页：版本看得见，命令只复制，本工具不代装

- 页头新增「检查更新」，新增 IPC `check_agent_versions`：对每个 agent 跑 `<cli> --version` 取本机版本，再查 npm 的 dist-tags 取上游 `latest`，行上出现 `2.1.296 → 2.1.317` 这样的徽标，页头记「检查于 刚刚」。
- **不执行任何安装或升级**。上游那套 brew/fnm/volta 锚定、卸载计划、升级确认框全部没搬。安装/升级命令做成行右侧的复制菜单，文本逐条抄自上游 `misc.rs`，由用户自己拿去终端跑。理由写进了代码注释：这些串永不进 argv，所以不存在「前端字符串变成一次执行」的路径。
- 版本表放在两处，各有分工：`AgentDescriptor` 新增 `npm_package`（只用于查最新版，是代码内注册表的事实），可复制的命令文本留在前端 `components/agents/installCommands.ts`（纯展示，且要在用户没点检查之前就能复制）。Qoder / Qoder CN 没有 npm 包，`None` 就**不查、不编 URL**，只报本机版本。
- 判定纪律：只有两边都解析得出来、且本机这份不是开发构建，才算可更新。`0.22.1+238.gdeadbeef`、canary/nightly/dirty 一律不标旧——误催一次升级比漏报一次更伤信任。新增 `services/version.rs` 手写 semver 比较（本项目没有 `regex` 依赖，上游 Rust 版不能直接搬）。
- 没塞进 `list_agents`：它是同步命令且被十来个面板共用，挂上 6 次子进程 + 6 次 HTTP 会让每次切页都变慢，还得把它改成 async 并重铺 10 个测试的 mock。`AgentStatus` 与那份 JSON 契约测试因此一字未动。

## 行为变化：批量启停也要排队

`set_skills_enabled` 是 Skill 侧唯一没挂 `begin_skill_job` 的写命令。批量铺链会往 agent 目录里 link，撞上正在替换真源目录的更新任务就可能链到半份内容上，所以这一版补上这把锁，互斥提示文案相应改成「已有 Skill 检查/更新/批量启停任务在进行」。

**代价要说清**：检查或更新进行中再点批量会被拒。前端因此在有任务在飞时锁住列头入口，但这是用户可感知的行为变化，不是纯内部加固。

## 行悬停补齐

`AssetRow` 本来就有 `hover:bg-subtle`，所以 Skills / MCP / 提示词 / 项目级一直是好的；真正没效果的是自己写行的那几处，这次统一补上 `transition-colors duration-150 hover:bg-subtle`：Skills **发现页**（两处行）、**未纳管页**、Agents 行、备份快照行、Git 提交行。顺带给 `AssetRow` 补上缺失的 `transition-colors`，否则共用行是硬切色、新补的几处是渐变，两种动画并存。

Git 提交行不是可导航的，但它行尾带自己的恢复操作，点亮读作「一条记录带它的控件」，与上面的快照行同一套语言，不留两页两种长相。

## 未做

- 列头批量只做 Skills。Rules / Subagents / Hooks 是「左列表 + 右侧 AgentMatrix」结构，压根没有列头，要批量得先给它们造一个列表头，另案。
- 不做鼠标十字定位（所在列也高亮），只做行。
- 版本探测只认 PATH 与常见安装目录里**第一份**命令；nvm 与 WSL 里的安装探测不到，只有 `.ps1` shim 的会报「未找到命令」。文案统一说「找到命令」，不说「已安装」。
- 子进程没有超时设施：某个 CLI 卡住会占住一个 blocking 线程。本版本不为它发明新原语。
- 暗色模式下行悬停只有 8/255 的色差（`--subtle #26262a` vs `--surface #2e2e33`），偏淡。**实测比较过 `bg-selected`，它在暗色下只差 3 档，更看不见**，所以保持 `bg-subtle` 不动。
